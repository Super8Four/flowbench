# Testing and evidence map

Tests use disposable archives, controlled loopback peers and synthetic or reserved-address fixtures. Keep production targets, credentials, user history and private visual references out of tests and public artifacts. This map identifies repeatable checks; it does not claim the latest working tree has passed them. Record the full source SHA with each result and use [lifecycle guidance](lifecycle.md) for release decisions.

## Test tiers and platforms

| Tier | How to run or verify | Boundary |
| --- | --- | --- |
| Focused regression | `python -m unittest discover -s tests -p test_matrix.py -v` (choose the affected file) | Run meaningful failure/compatibility cases, then the required broader checks; avoid repeated runs without new changes or concerns |
| Full Python suite | `python -m unittest discover -s tests -v` with the verified engine and application dependencies | Read skips and native-tool availability; mocked results prove adapter logic only |
| Base container lifecycle | `python3 scripts/check-container.py iperf-workspace:local` after building the intended source | Creates its own containers/volume; checks native traffic, storage and reports under non-root/read-only/capability limits |
| Actual optional Flent | [Derivative image](../scripts/Flent.Dockerfile) and [check-flent.py](../scripts/check-flent.py), using the workflow's isolated command | Real pinned Linux tools and owned loopback Netserver; no external network, host privilege changes or release-image bundling |
| Report rendering | [check-reports.py](../scripts/check-reports.py) creates PDF/DOCX fixtures; render PDFs and office-converted DOCX PDFs, then inspect every page | Structural assertions and PNG generation do not replace visual inspection |
| Browser interaction | Actual app with a disposable archive on desktop, mobile and keyboard navigation | Static HTML tests do not exercise layout, focus, chart paths or repeated interactions |

| Platform | Checks and limits |
| --- | --- |
| Windows, Python 3.12, pinned iPerf3 | Full suite and controlled loopback traffic; verify native diagnostics where legitimately available. Bidirectional UDP is explicitly rejected by the bundled engine; native Flent is unavailable |
| Ubuntu 24.04 AMD64 | Native CI suite, base lifecycle, derivative Flent and report rendering; retain exact-SHA terminal job result |
| Ubuntu 24.04 ARM64 | Same native checks on the ARM runner; emulator or AMD64 success cannot stand in for it |
| Physical Raspberry Pi / other native hosts | Deployment, host permissions, external-peer reachability, performance and hardware durability need separate target acceptance; CI does not establish these |

## CI and evidence

Both [source/Windows checks](../.github/workflows/quality.yaml) and [native container checks](../.github/workflows/container.yaml) run on pushes, pull requests and manual dispatch. A newer run on the same ref cancels superseded work. Verify the tested checkout SHA and the terminal results of both workflows; a pull request can test a merge commit rather than only the feature head.

The source job uses Python 3.12 and Node 24 to parse first-party Python, check JavaScript syntax, verify local documentation targets/action pin format and exercise the Flent DOM/API fixture. Run it locally with `python scripts/check-source.py` and `node tests/workflows-flent-behavior.mjs`. External URLs, rendered layout and runtime behavior need their own checks. The Windows job installs the application dependencies and the checksum-verified community iPerf3 3.22 build using the repository installer, then runs every Python test with disposable loopback peers. Its JSON summary identifies the tested source, test count, failures, errors and skips; unavailable native Windows Flent is not claimed as passed.

Workflow actions are pinned to the current stable releases checked on October 12, 2026 through official `actions/*` release/tag/commit endpoints and their runtime manifests: checkout v7.0.1 `3d3c42e5aac5ba805825da76410c181273ba90b1`, setup-python v7.0.0 `5fda3b95a4ea91299a34e894583c3862153e4b97`, setup-node v7.1.0 `949feb2413d6458794dcd2491c4babbbce0c15c1`, upload-artifact v7.0.2 `cf430e030ddbb5b0abf93d22962f4752f3646cd9`. All use the supported Node 24 action runtime; hosted runners must supply Actions Runner 2.327.1 or newer. The selected Python/cache, Node and archived-upload inputs were checked against those manifests and release notes. No registry authentication is configured, and automatic Node package caching is disabled because this project has no Node dependencies. Both workflows request only `contents: read`, disable persisted checkout credentials, use standard hosted runners and have no deployment or release-publishing step. No pull-request secrets or privileged pull-request trigger is used.

Each native job validates Compose, builds/checks architecture, runs the complete suite and base lifecycle, then tests actual Flent in a separate pinned derivative image with `--network none`, dropped capabilities and no new privileges. The derivative image is not uploaded as a release download. Report fixtures are generated and rendered using LibreOffice/Poppler; report QA artifacts can be produced after lifecycle success even when another check fails. Their presence is not a successful overall CI result. Non-PR successful packaging writes image archives, inspection metadata and checksums. Source/Windows/container summaries and synthetic report fixtures are retained for 14 days; runtime archives, private data and credentials are not uploaded. Read the actual terminal status of every required job and step.

[Dependabot](../.github/dependabot.yml) checks pip and action dependencies weekly with grouped updates and one open version-update PR per ecosystem, allowing at most two regular update PRs across those groups. This limit does not control separately enabled security-update PRs. Updates receive the same test gates and manual review; they do not merge automatically. [PR](../.github/PULL_REQUEST_TEMPLATE.md), [bug](../.github/ISSUE_TEMPLATE/bug_report.md) and [release](../.github/RELEASE_CHECKLIST.md) templates record useful evidence. Release promotion remains an explicitly authorized manual action after exact-source checks, artifact/checksum verification and browser/report review; there is no automatic publishing or deployment.

An authorized new `v*` tag triggers the same native tests and packaging; its name must exactly match `app/version.py`. Image labels, inspection metadata and checksum files identify the tested source SHA, version and architecture. Download artifacts from that exact successful run, verify them before any manual publication, and preserve every existing release/tag. A development-branch image or an old successful run is not proof for a newer release commit.

Keep an evidence record with source SHA, app/tool versions, platform, command or CI run link, test counts including skips, failures, screenshot/render artifact location and unresolved limits. Archive failure, permission-blocked probes or a failed native Flent step must remain visible. A later fix requires a new exact-source result; earlier green base-container checks cannot erase a failed optional integration.

For browser QA, cover empty history, project baseline selection, matrix start/stop/restart, diagnostic absence/errors, annotations, live gaps, repeated starts and imports, and report preview/download/redaction. Exercise DNS negative responses and timeout states, ICMP unknown denominators and upper-bound RTTs, same-type check comparisons, Run again review/cancel/confirm and Retry same request without duplicate starts. Verify timezone changes display the same saved instant without rewriting canonical UTC evidence. For larger throughput comparisons, check five or more mixed-duration runs, adding/removing rows, saved colors, legend wrapping, shared SI axes, horizontal scrolling and keyboard focus on desktop/mobile. Use only synthetic fixtures. Review console errors and verify a failed request does not display fabricated success.

For report QA, inspect every page of single-run, redacted multi-run, native-format Flent, DNS-check and ICMP-check fixtures in both PDF and rendered Word output. Check charts, captions, units, color/label identity, pagination, clipping and redaction. The native [layout checker](../scripts/check-report-layout.py) verifies text retention, comparison heading/table grouping and rejection of header/footer-only pages; [test_report_layout.py](../tests/test_report_layout.py) retains regressions for defects that global text checks missed. Fixture generation is described in [reports](reports.md); actual Flent setup is in [Flent](flent.md). [Verification](verification.md) records exact-source screenshots and render evidence, including historical releases, which must not be relabelled as proof of a newer commit.

No check here establishes physical power-loss recovery, Pi deployment, external network acceptance, full WCAG compliance, complete canonical acceptance, authentication or a support SLA. Use [requirements](requirements.md) and [lifecycle](lifecycle.md) to preserve those boundaries.
